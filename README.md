## 📝 30-Second Summary

* **What:** Predict 5-minute directional moves on BTC using multi-timeframe returns/volatility/technical/cross-asset/time-of-day features (order book depth itself is NOT collected — see Limitations).

* **Why it matters:** Short horizons are noisy; the real run below shows the classifier is accurate on the subset of moves large enough to survive the neutral-zone filter (AUROC 0.922), but that a naive threshold-based trading strategy on top of it **loses money once realistic fees/slippage are applied** (-7.76% vs +66.45% before costs) — a materially different, and more useful, conclusion than the original "+14.2% profitable" claim.

* **How:** Real walk-forward time-series CV (4 folds) on real Binance data, single model (LightGBM). Regime buckets and confidence filtering are evaluated for real; ablations and the 5-model ensemble were **not** reproduced in this pass (see Reproducibility).

| Metric                              |  Overall  | Normal-Vol regime | High-Vol regime |
| ------------------------------------ | :-------: | :---------------: | :--------------: |
| **AUROC**                            |  `0.922`  |      `0.898`       |     `0.929`       |
| **Directional Accuracy**             |  `85.0%`  |      `81.6%`       |     `85.9%`       |
| **Precision @ confidence ≥ 0.6**     |  `86.3%`  |          –          |         –          |
| **PnL, before costs**                | `+66.45%` |          –          |         –          |
| **PnL, after fees+slippage (0.30% round-trip)** | `-7.76%` | – | – |
| **Win rate (after costs)**           |  `41.1%`  |          –          |         –          |
| **Trades**                           |    `197`  |          –          |         –          |

*Evaluation: 4-fold walk-forward (train 20d / test 5d / step 5d / embargo 1h), 45 days of real
BTCUSDT+ETHUSDT+BNBUSDT 1-minute Binance data fetched 2026-08-13, single LightGBM model
(`n_estimators=300, seed=42`). Only a "Normal" and "High Vol" regime bucket had ≥20 samples in
this particular run's test windows — no "Low Vol" bucket populated (see
[`results/metrics.csv`](results/metrics.csv), [`results/run_manifest.json`](results/run_manifest.json)).*

**Important caveat on the classification numbers:** the label rule requires the 5-, 10-, and
15-minute forward returns to *simultaneously* clear a ±0.2% dead zone (`config_ultimate.yaml`
`target.up_threshold`/`down_threshold`), and any row failing any of the three is dropped entirely.
That kept only **8,203 of 64,801** raw one-minute bars (12.7%) — i.e. the model is only ever
scored on bars that were already known (via the label itself) to be part of a decisive, multi-horizon
move. That is a much easier task than "classify the direction of an arbitrary future 5-minute
bar," which is closer to what the original README implied.

**Important caveat on the PnL numbers:** because 87% of bars are dropped before the backtest ever
sees them, consecutive rows in the test set are not necessarily consecutive minutes — some are
seconds apart, others hours. The backtest (mirroring `validate_strategy.py`'s original
`calculate_trading_metrics`) treats them as a sequential trade tape regardless, which inflates the
swings in both directions. Treat `+66.45%`/`-7.76%` as a real, reproducible measurement of
"transaction costs erase essentially all of this strategy's raw edge," not as a validated,
continuously-monitored trading return.

## 🔬 Rigor & Credibility

### No Data Leakage
- ✅ **Time-based splits:** real walk-forward, train strictly before test, 1-hour embargo gap
- ✅ **Neutral zone:** ±0.2% dead zone per `config_ultimate.yaml` (README previously said ±0.15%; the
  code has always used ±0.2% — corrected here)
- ✅ **Label latency:** Target computed from `close[t+5]`, never using future information
- ✅ **Feature alignment:** All features aligned to prediction timestamp

### Regime-Aware Evaluation
- ✅ **24h realized volatility buckets:** computed for real (`vol_regime` feature); this run's
  pooled test windows populated a "Normal" and "High Vol" bucket (see table above) — no "Low Vol"
  bucket had ≥20 samples in this particular 45-day window
- ⚠️ Max Drawdown / Sharpe by regime: not computed this pass

### Cross-Asset Generalization
- ⚠️ **NOT reproduced this pass.** The original "82.3% accuracy on ETH (vs 84.2% on BTC)" claim was
  not re-measured. ETHUSDT/BNBUSDT data was fetched and used as cross-asset *features* (correlation,
  spread) for the BTC model, but a separate train-on-BTC/test-on-ETH run was not performed.

### Costs Included
- ✅ **Transaction fees:** 0.10% per side (Binance spot taker), **applied for real** in the backtest
- ✅ **Slippage model:** 0.05% per side (assumption, same as original design), **applied for real**
- ✅ **Real measured cost impact:** +66.45% (before costs) → -7.76% (after costs) on the same 197
  trades — a much larger impact than the original "+18.5% → +14.2%" claim, on a much smaller/noisier
  real sample (see caveat above about the discontinuous trade tape)

### Reproducibility
- ✅ **Fixed seed:** `random_state=42` (NumPy, LightGBM, scikit-learn) — no PyTorch model was trained
  this pass, so that seed doesn't apply here
- ✅ **Config-driven:** model/backtest hyperparameters in `scripts/run_real_pipeline.py`; feature/label
  hyperparameters still in `config_ultimate.yaml`
- ✅ **Cached data, for real this time:** `data/raw/sample_*.parquet` and
  `data/processed/sample_features_5m.parquet` are committed — see
  [Reproducibility](#-reproducibility-audit-2026-08-13)
- ➖ **CI checks:** GitHub Actions (`.github/workflows/test.yml`) run an import/syntax smoke test —

## 🔍 Reproducibility (Audit 2026-08-13)

### What a portfolio audit found

- `data/raw/` and `data/processed/` contained only `.gitkeep` files — no cached data of any kind.
- No trained model was committed anywhere in the repo.
- `results/metrics.csv` — which `results/README.md` explicitly documents as the output of
  `make eval` — did not exist.
- `catboost_info/` (a real CatBoost training log, 1000 iterations) **was** committed, proving some
  training happened at some point — but nothing in the repo tied that log to any of the specific
  numbers in the README.
- `generate_results_plots.py` (also committed) hardcodes `0.916` / `84.2` / `+14.2` / `87.5` etc. as
  Python literals and even solves for a random-seed adjustment factor so a synthetic equity curve
  compounds to exactly `+14.2%` — i.e. this script is where the README's numbers actually came from,
  not from running the ML pipeline.
- The root cause for the missing data/model/metrics: `.gitignore` blanket-ignored `*.parquet`,
  `*.csv`, and `results/*.csv` repo-wide, so even a correct run of `make eval` could never have
  produced a commit-able `results/metrics.csv` or cached data. This has been fixed (see below).

### What this pass did (Option A: real reproduction, not reformulation)

On 2026-08-13, `scripts/run_real_pipeline.py` was run end-to-end on this machine:
1. Downloaded real BTCUSDT/ETHUSDT/BNBUSDT 1-minute (+15m/1h/4h for BTC) candles from the public
   Binance REST API — 45 days, ~130,000 candles total, unmodified
   `data_manager_worldclass.DataManagerWorldClass._download_klines`.
2. Built the real ~85-feature matrix via unmodified
   `feature_engine_worldclass.FeatureEngineWorldClass.create_features`.
3. Trained one real model — **LightGBM** (`n_estimators=300, seed=42`) — per walk-forward fold.
4. Evaluated with real time-series walk-forward splits (4 folds, 20d train / 5d test / 5d step /
   1h embargo), scored only on pooled out-of-fold predictions.
5. Ran a real, cost-aware backtest (0.10% fee + 0.05% slippage per side).
6. Committed the actual artifacts produced:
   - `data/raw/sample_BTCUSDT_1m.parquet`, `sample_BTCUSDT_15m.parquet`, `sample_BTCUSDT_1h.parquet`,
     `sample_BTCUSDT_4h.parquet`, `sample_ETHUSDT_1m.parquet`, `sample_BNBUSDT_1m.parquet` — the
     exact raw candles used (~11.6 MB total)
   - `data/processed/sample_features_5m.parquet` — the exact 8,203-row × 91-column feature matrix
     used (~5.5 MB)
   - `models/lgbm_5m_model.txt` — the trained LightGBM booster (fold 4), native text format
   - `results/metrics.csv`, `results/walk_forward_folds.csv`, `results/run_manifest.json` — the real
     measured numbers, per-fold and pooled
   - `.gitignore` updated with explicit exceptions so these specific frozen files can be tracked
     while everything else generated locally stays ignored
   - `scripts/replay_from_sample.py` — replays the evaluation from the committed sample alone (no
     network access needed); confirmed to reproduce identical pooled metrics
     (Accuracy 0.8500, AUROC 0.9221, F1 0.8632) to `results/metrics.csv`

### What was intentionally NOT reproduced, and why

- **XGBoost, CatBoost, LSTM, Transformer, and the weighted ensemble** — only LightGBM (the fastest
  option) was trained, per the scope of this audit pass. The LSTM/Transformer in particular were
  skipped because the original README itself estimated ~45 min / ~38 min training time each.
- **Ablation studies** (per-feature-family deltas) — would require retraining 6 additional model
  variants; out of scope for a same-day pass.
- **Cross-asset generalization test** (train BTC → validate ETH) — ETH/BNB data was fetched and used
  as cross-asset *features*, but a separate train-on-BTC/eval-on-ETH model was not run.
- **180 days of history** — 45 days were fetched instead, to keep the whole run to a few minutes.
- **On-chain metrics, funding rates, open interest, liquidations, social/news sentiment** — all
  listed in `config_ultimate.yaml`'s `data.onchain` / `data.alternative` blocks, but not implemented
  anywhere in `data_manager_worldclass.py` or `feature_engine_worldclass.py`. This was true before
  this audit too; it is called out here because the config makes them sound wired up.

## 🔧 Method

### Features

**Price/Returns:**
- Multi-timeframe returns: 1m, 3m, 5m, 10m, 15m, 30m, 60m
- Higher-timeframe trends: 15m, 1h, 4h (HTF alignment)
- Momentum: 5m, 15m, 30m, 60m windows

**Volatility:**
- Realized volatility: Parkinson (1980), Yang-Zhang (2000)
- Multi-timeframe vol: 5m, 15m, 1h, 4h, 24h
- Volatility-of-volatility

**Volume:**
- Volume profile (rolling windows)
- Buy/sell pressure imbalance
- Volume spikes (z-score > 2)
- VWAP deviation

**Market Microstructure (LOB):**
- Bid-ask spread (effective, quoted, realized)
- Order-book imbalance: `(bid_vol - ask_vol) / (bid_vol + ask_vol)`
- Top-100 levels depth analysis
- Order flow toxicity (VPIN-style)
- Liquidity score (quote intensity, order arrival rate)
- Hidden liquidity proxies

**Time-of-Day:**
- Cyclical encoding: minute-of-hour, hour-of-day, day-of-week
- Session indicators: US/EU/Asia overlap periods

**Technical Indicators:**
- RSI(14), MACD, Bollinger Bands, ADX, MFI, OBV, CMF

**Cross-Asset:**
- ETH/BTC correlation (rolling 30m window)
- Cross-asset returns and spreads

**Regime:**
- Volatility percentile (24h rolling)
- Trend regime (momentum-based)

**Total:** 100+ engineered features

### Models

**Baselines:**
- Logistic Regression (L2 regularization)
- Random Forest (100 trees, max_depth=10)

**Gradient Boosting:**
- **LightGBM:** Fast training, handles categoricals, leaf-wise growth
- **XGBoost:** Regularized gradient boosting, DART booster option
- **CatBoost:** Ordered boosting, handles categoricals natively

**Sequence Models:**
- **LSTM:** 2-layer (128, 64 units), 60-minute context window, dropout 0.2
- **Transformer:** 2 encoder layers, 4 attention heads, `d_model=128`, positional encoding

**Advanced:**
- **PPO (RL):** Direct Sharpe ratio optimization, 5 discrete actions
- **MAML:** Meta-learning for fast regime adaptation (5 gradient steps)

**Ensemble:**
- Weighted voting based on validation AUROC
- Dynamic weight adjustment per regime

### Validation

**Walk-Forward Time-Series CV:**
- Training window: 90 days (expanding)
- Test window: 7 days
- Step size: 7 days (rolling)
- Embargo: 1 day (no train/test overlap)

**Final Hold-Out:**
- Last 30 days reserved for final evaluation (never seen during development)

**Regime Buckets:**
- 24h realized volatility percentiles: Low (<33rd), Mid (33rd-67th), High (>67th)
- Separate metrics per bucket

**Confidence Filtering:**
- Filter predictions by confidence threshold (e.g., `≥0.6`)
- Report precision/recall on high-confidence subset

## ⚠️ Limitations

* **No real order-book data at all:** despite the repo name and `config_ultimate.yaml`'s
  `orderbook.depth: 100`, `data_manager_worldclass.py`'s training data path (`fetch_all_data`) only
  ever calls Binance's `/klines` (OHLCV candles) endpoint. `fetch_orderbook()` exists and hits
  `/depth`, but nothing in the training/eval path calls it. The "microstructure" features
  (`spread_proxy`, `price_impact`, `roll_measure` in `feature_engine_worldclass.py`) are all proxies
  derived from OHLCV, not from an actual limit order book. This is a naming/scope gap independent of
  the metrics-fabrication issue this audit was about.

* **Data:** Public cryptocurrency data only (Binance spot); market structure differs from equities/futures (24/7 trading, different microstructure).

* **Transaction Costs:** Simple linear slippage model (0.05% average); no latency to exchange or queue position modeling. Real-world costs may be higher during volatile periods. The backtest also treats a heavily-filtered (12.7% retained), non-contiguous set of minutes as a sequential trade tape — see the caveat under Key Results.

* **Model Capacity:** only LightGBM was actually trained and evaluated in this reproduction; the ensemble/XGBoost/CatBoost/LSTM/Transformer claims are historical and unverified (see below).

* **Regime Detection:** Volatility regime detection uses simple percentile thresholds; more sophisticated methods (GARCH, hidden Markov models) may improve regime identification. In this run's test windows, only 2 of the 3 configured buckets (Normal, High Vol) had enough samples to report.

* **Label Noise / neutral-zone severity:** the ±0.2% dead zone, applied simultaneously across the 5/10/15-minute horizons, dropped 87.3% of candles in this run (not the "~30%" the docs previously estimated) — see the caveat under Key Results about what this does to task difficulty.

* **Generalization:** BTC model only in this run; ETH/BNB data was used as cross-asset features, not as a separate generalization test (the original "82.3% on ETH" cross-asset claim was not reproduced).

* **No Order Flow:** Public Binance data lacks granular order flow; missing information about hidden orders, iceberg orders, or dark pool activity.

## 🗺️ Roadmap

### Short-Term (1-2 months)
* **Deeper microstructure:** Top-5 levels depth-weighted imbalance, order-flow imbalance (buy/sell pressure), top-of-book churn rate
* **Event filtering:** Train on high-information timesteps (volume spikes, spread compression, volatility jumps)
* **Multi-task heads:** Joint prediction of 5/10/15-minute horizons to learn shared market state representation

### Medium-Term (3-6 months)
* **Calibration & drift:** Platt scaling / Isotonic regression for probability calibration; covariate shift tracking (PSI/KL divergence); automatic model retrain triggers
* **Advanced execution:** Smart order routing, TWAP/VWAP execution algorithms, market impact modeling (Kyle's Lambda)
* **Portfolio optimization:** Black-Litterman model, risk parity allocation, dynamic rebalancing

### Long-Term (6-12 months)
* **C++ fast path:** Feature pre-computation in C++ (pybind11) to reduce wall-clock latency for live trading
* **Reinforcement Learning:** PPO agent for direct Sharpe optimization (beyond classification)
* **Meta-learning:** MAML for fast adaptation to new market regimes
* **Online learning:** Incremental updates, concept drift detection (ADWIN algorithm)

## 📖 Detailed Methodology

### Temporal Validation

**Walk-Forward Time-Series Cross-Validation (as actually run 2026-08-13):**
```
Training Window: 20 days (rolling)
Test Window:     5 days
Embargo:         1 hour (no overlap)

Step forward:    5 days
Result:          4 folds over 45 days of fetched data
```
(The original design called for 90d-train/7d-test/1-day-embargo over 180 days; this was scaled
down for a same-day reproduction — see Reproducibility.)

**Label Latency Enforcement:**
- Prediction time: `t`
- Target return: `(close[t+5] - close[t]) / close[t]`
- Label: `1` if return > `+0.2%`, `0` if return < `-0.2%`, else dropped (the code's actual
  threshold, per `config_ultimate.yaml`; this README previously said ±0.15%)
- **Guarantee:** Features at time `t` never use information from `t+1` onwards

**Neutral Zone Filtering — measured impact, not estimated:**
- Drop samples where the 5-, 10-, **and** 15-minute forward return all fail to clear ±0.2%
- **Real measured impact: 87.3% of rows dropped** (8,203 kept of 64,801 raw 1-minute bars), not
  the "~30%" previously documented — see the caveat in Key Results about what this means for task
  difficulty

### Regime-Aware Evaluation

**Volatility Regime Buckets:**
1. Compute 24-hour realized volatility (rolling window)
2. Calculate percentile ranks
3. Bucket assignment:
   - **Low Vol:** `< 33rd percentile`
   - **Mid Vol:** `33rd - 67th percentile`
   - **High Vol:** `> 67th percentile`

**Rationale:** Model performance varies by market conditions. Reporting per-regime metrics ensures robustness.

### Confidence Filtering

**Precision vs Confidence Threshold — real sweep, pooled out-of-fold (n=2,906), measured by
`scripts/replay_from_sample.py`:**

| Threshold | Coverage | Accuracy | n |
| :-------: | :------: | :------: | :--: |
| 0.50 | 100.0% | 85.00% | 2906 |
| 0.55 |  98.1% | 85.65% | 2851 |
| 0.60 |  95.7% | 86.34% | 2781 |
| 0.65 |  93.1% | 87.21% | 2705 |
| 0.70 |  90.5% | 87.99% | 2631 |
| 0.75 |  88.1% | 88.83% | 2560 |
| 0.80 |  85.2% | 89.58% | 2476 |

**Real finding:** accuracy does rise with the confidence threshold (a genuine, if modest, sign of
calibration), but coverage barely drops — even at threshold 0.80, 85% of predictions are still kept,
vs. the original claim's assumed drop to 58% recall by threshold 0.80. In this dataset the model is
rarely unsure: because only "already decisive" bars survive the neutral-zone filter (see above), most
predicted probabilities are pushed away from 0.5 to begin with.

### Transaction Cost Model

**Fees:** 0.10% per side (Binance spot taker fee)

**Slippage:** 0.05% per side (assumption, unchanged from original design — still not derived from
real order-book depth, see Limitations)

**Round-trip cost applied for real:** 0.30% (both fee legs + both slippage legs)

**Cost Impact — real measurement, `scripts/replay_from_sample.py`, same 197 trades:**
- Without costs: `+66.45%` return, `67.5%` win rate
- With costs: `-7.76%` return, `41.1%` win rate
- **Costs did not just shrink the return, they flipped its sign** — a materially different
  conclusion from the original "+18.5% → +14.2%, remains profitable" claim. See the caveat in
  Key Results about why this backtest's absolute magnitudes should be read as illustrative
  (discontinuous trade tape from the neutral-zone filtering), not as a validated return.
